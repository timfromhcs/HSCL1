# SOTA scan — 2026-11-06 (before continuing implementation)

Scope: everything the owner asked for in the last two turns — faster ISO builds, delta/update delivery, screenshot & visual QA
automation, delegation economics, mid-flight model training, and **neural networks for games + LLM-authored artefacts** inside the OS.
Each item: what the state of the art is, what is actually feasible on the target hardware (Ryzen 7 7735HS, Radeon 680M, 24 GB RAM,
no CUDA, Vulkan 1.3), and what HSCL1 will do — including what it will *not* claim.

---

## 1. Neural game engines / world models

| Work | Claim | Reality check for HSCL1 |
|---|---|---|
| **GameNGen** (Google, arXiv 2408.14837) | DOOM simulated entirely by a diffusion model, >20 FPS, stable multi-minute play | 20 FPS on **one TPU**; a 680M iGPU is ~2 orders of magnitude short. Not shippable as a "neural game engine". |
| **Genie 3** (DeepMind, 2025) | prompt -> navigable 720p world at 24 FPS, consistent for minutes | Closed, hosted, huge. Reference for direction only. |
| **Neural Cellular Automata** — "From Cells to Pixels", SIGGRAPH 2026 (arXiv 2506.22899), `NCAtorch`, Monash NCA | learned local update rule, self-organising, regeneration, **runs in WebGPU in a browser** | This is the shippable end of the spectrum: a few-thousand-parameter conv net, real-time on integrated graphics, trainable on CPU in minutes. |
| **TensorFlow Playground** style tiny nets | in-browser training of a small MLP on a 2-D problem | trivially portable, good teaching demo, MIT/Apache. |

Decision: HSCL1 ships **small, honest neural demos** (NCA playground, tiny-net trainer, a next-frame prediction toy), not a GameNGen
clone. The toy frame predictor is labelled *"toy: 64x64, one game, not a game engine"* in the UI, because that is what it is.

## 2. "LLM writes the game/thing directly"

- Agentic coding is now measured on **SWE-bench Verified** and repo-scale tasks; the consensus in 2026 write-ups is that the model is
  not the bottleneck — the *verification loop* is (Sonar, Dan Luu, MindStudio summaries). A one-person workflow can generate more code
  than can be reviewed, so the shipped workflow must make verification automatic.
- **Grammar-constrained decoding** (GBNF in llama.cpp, XGrammar in vLLM, Outlines) guarantees *structural* validity of the output but
  not *semantic* correctness. That is exactly the right tool for a small local model: let it fill a validated schema instead of
  free-writing a whole program.
- Practical failure mode documented repeatedly: schema-valid but nonsense. So the pipeline needs a render/run step that proves the
  artefact works, not just parses.

Decision (HSCL1 "Game Studio" / `hscl code`):
1. Prompt -> **game spec JSON** under a GBNF grammar (title, template id, palette, difficulty, entities, win condition).
2. A vetted, offline **template runtime** (snake, breakout, maze, platformer-lite) renders the spec into a single self-contained HTML
   file in `~/Projects/NeuralLab/games/`.
3. The result is opened in an isolated renderer and smoke-checked (canvas non-blank, no console error, deterministic seed).
4. Free-form code generation stays in `hcscoder`, and anything it produces runs **inside the sandbox**, never on the host as root.

## 3. Small models that can actually live on this machine

- 2026 SLM landscape: "small" now means sub-4B; 0.5-1.5B models need <2 GB at 4-bit and are explicitly targeted at on-device use
  (Intuz, VDF, Premai round-ups). Apache-2.0/MIT now covers most of that range.
- Fine-tuning guidance: fine-tune only where the task repeats and is narrow; **always run a general-capability holdout after a
  fine-tune**, because domain accuracy can rise while instruction-following silently regresses (Vercel, Fastino).
- Our own measurement stands: Qwen2.5-Coder-1.5B Q4_K_M (1.11 GB) on Vulkan, 32K ctx with KV quantisation, already the local engine.

Decision: ship a **bundle**, not a giant model: `hcsl-route` (0.5B, classification/booleans), `hcsl-chat` (1.5B, short offline help),
`hcsl-nca` (tiny NCA weights), each with card + licence + sha256 + eval report. Catalogue entries are opt-in downloads, ISO stays lean.

## 4. Build speed and update delivery

- Compression benchmarks (MaskRay 2025, Redpill Linpro 2024): zstd-19 is within ~6 % of xz-6 size at comparable per-thread speed but
  parallelises better; zstd-15 is far faster at ~8-10 % larger. **Measure on our own tree** — do not guess.
- Ubuntu now builds ISOs directly in `livecd-rootfs` (`isobuild`), and `livefs-editor` (ubuntu/livefs-editor) edits a live ISO
  in place. Canonical route, but a pipeline rewrite; evaluate at 1.0, not now.
- Delta delivery: Ubuntu publishes **`.zsync`** next to every ISO — a user re-syncing gets only changed blocks. Cheap for us
  (`zsyncmake`), big win for users, no server changes needed (GitHub supports Range requests — must verify).
- Image-based delta updates (OSTree static deltas: 0.09 MB vs 129 MB full; casync/desync) replace APT with an immutable image model.
  That is a 2.x architectural decision, not a v1 patch.

Decision: v1 keeps APT; adds build-stage timing budgets, package/rootfs caches, per-package build skipping, compression bake-off, and
`.zsync` for ISO downloads. Documented in plan Track C/D.

## 5. Visual QA

- Playwright `toHaveScreenshot()` with committed baselines is the default open-source answer in 2026 comparisons; baselines must be
  produced in the same environment as the comparison (font/renderer drift is the main flake source). `reg-suit`/Argos are optional
  git-aware/review layers; no vendor needed.
- For a **desktop OS** there is no off-the-shelf product: capture must be in-guest and deterministic (fixed clock, fixed resolution,
  animations off) and transported to the host. Serial streaming is fragile; a **virtio-9p/virtiofs share** is the robust path.

Decision: plan Track E — deterministic QEMU matrix + 9p share + perceptual diff with committed baselines + Playwright for the site.

## 6. Delegation economics (owner request)

Local System-1 tooling exists (`jev_choice`, `jev_noul`, `jev_score`, `jev_route_subagent`) plus local subagents and the RSI/LoRA loop
(`lora_train_session`, `lora_merge_adapter`, `lora_auto_rsi_cycle`). The binding constraint is *trust*: a 1.5B subagent is a hint,
never evidence. Plan Track A/B encode that: delegate the mechanical, verify with `grep`/`git`, train between sprints, ship only what
beats the previous generation on a held-out evaluation.
