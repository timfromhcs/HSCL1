# Known limitations (truthful list)

Status of this document: maintained with every phase. Last reconciliation: 2026-11-08, source `d9a6f02`; local pre-release set `0.1.3-alpha.0` is an older image from `a55e023` (2026-11-07), not a v1 release candidate.

HSCL1 is **pre-alpha**. Nothing below has been tested on physical hardware. Rows are corrected whenever an earlier status turns out to
be stale - a limitation list that lags behind reality is a false claim in the other direction.

Image evidence is bound to its build. The local `0.1.3-alpha.0` ISO has SHA-256 `fc81ad1d93efeac61904879e9def34e39cdceb982bf7aafc070b34afdd4d1ebb`; its release notes explicitly leave installation on that exact image unverified. The separate `artifacts/install-0.1.3-alpha.0/result.json` reports `reached_desktop: false` and is not a successful install test. Earlier successful installations remain historical evidence. Secure Boot file signatures are not firmware acceptance. See [release readiness audit](research/2026-11-08-release-readiness-audit.md).

| Area | Status | Limitation |
|---|---|---|
| Bootable ISO | VM-VERIFIED (pre-alpha) | A remastered ISO boots to the HCS desktop in QEMU (UEFI, BIOS, Secure-Boot firmware). Not tested on physical hardware; not published; no release signatures yet. |
| Secure Boot | partially verified | The image boots under OVMF Secure-Boot firmware with Microsoft keys. The Secure Boot state inside the guest has not been read yet, so no Secure Boot claim is made. What *is* measured (2026-11-07, `scripts/sb_evidence.py` on the released 0.1.2 ISO): the shim `EFI/boot/bootx64.efi` carries a Microsoft certificate ("Microsoft Windows UEFI Driver Publisher" / "Microsoft Corporation UEFI CA 2011"), and `grubx64.efi`, `mmx64.efi` and `casper/vmlinuz` carry Canonical's "Secure Boot Signing (2022 v1)" certificate. A signature on the file is not firmware acceptance - that stays gate G6. |
| Installer | VM-VERIFIED (pre-alpha) | Upstream Kubuntu Calamares **3.3.14** (from `resolute-updates`) installs to a 40 GiB virtual disk; the installed system boots and logs in. Offline install works. **Not done:** installer fault injection, branding of every Calamares page, dual-boot, physical disks. Two upstream defects are documented below. |
| LUKS2 | VM-VERIFIED (pre-alpha) | Automated Erase-disk + Encrypt install on a disposable disk; installed system boots, wrong passphrase is rejected, correct one reaches the desktop; `aes-xts-plain64`/`argon2id`, no keyfile in `crypttab`, initrd or `/`; marker passphrase absent from the scanned logs. **Not done:** recovery-key flow, TPM-backed unlock (not offered), Secure Boot combined with encryption, `/boot` and the initrd are unencrypted and not integrity-protected. |
| `hscl` CLI | TESTED (unit) | Implemented: `version`, `about`, `status`, `system info`, `security status`, `ai detect`, `doctor`. Not yet run on an installed HSCL1 system. |
| Security Lab | specification/builder probe TESTED; HSCL1 runtime PLANNED | `hscl lab` generates restricted argv; it does not execute containers. The existing `containers/kali/image.pin` was pulled/inspect-verified and restricted run/basic-toolset install tested on the WSL builder on 2026-11-08. Podman is still absent from the existing HSCL1 image; guest isolation, explicit mounts, CLI execution and installer integration remain open. `passt` is required for the tested default user-mode networking. See the builder-probe research note; no VM/release gate is closed by this experiment. |
| Privacy mode | PLANNED | HSCL1 is **not Tails** and makes no anonymity claim. |
| Local AI | partially verified | Hardware detection, model catalogue, download with sha256 check and a CPU chat completion with one 2B model are verified on the builder. Vulkan/GPU, MTP and TurboQuant are NOT verified. |
| Hardware | none verified | No device is listed as supported. |
| Languages | partial | Handbook (EN/DE/FR) and Control Center strings (EN/DE/FR) exist; installer, boot menu and desktop defaults are still English/Kubuntu. |
| Test environment | note | `/dev/kvm` is present in the WSL2 build lab since 2026-11-06 (earlier plan text said otherwise), but the automated install gates still run under WHPX/TCG for Secure Boot coverage, so they remain slow. |
| Trademarks | rules encoded, human review pending | `docs/TRADEMARKS.md` + `scripts/check_trademarks.py` enforce the mechanical part of OffSec's policy (symbol + attribution sentence on first mention, no modified/combined mark, no mark in a domain name) and forbid Kali/Tails logos and "HSCL1 Tails"/"HSCL1 Kali Edition" wording. Legal review of the derivative-distribution naming and of Canonical's IP policy is still **owner work**. |
| Window tiling | PLANNED, route corrected (KDE bug 466019 still open, checked 2026-11-07) | KWin does not persist custom tile layouts (KDE bug 466019) and loses them on monitor changes. HSCL1 plans reviewed **presets**, but a `kwinrc` default cannot be shipped: KWin stores tiling under `[Tiling][<virtualDesktopId>][<outputUuid>]` with a fallback key derived from the output's name/eisaId/model/serial, i.e. per machine. The supported route is a KWin script (plan W5.5); until one exists, nothing in the desktop offers "saved layouts" and no default layout is claimed. |
| Local AI, memory | measured limits, no SSD spill | The GPU-accessible memory of an APU is GTT, raised only by `ttm.pages_limit` (default half of RAM) and only before the driver initialises - there is no live switch. `llama.cpp` has **no supported way** to keep weights or KV cache on an SSD: what touches disk is the page cache, swap/TTM swapout and `--load-mode dio`. Any "SSD as VRAM" feature is unimplemented and must not be offered. |
| Flatpak | not installed by default | The base does not ship Flatpak (Canonical asked the flavours to stop). It is a documented opt-in switch in the Control Center; any Flatpak application is the user's own choice and its sandbox is not verified by us. |
| Installer, multiple encrypted disks | upstream defect, fix in the archive, unmeasured here | Calamares does not finish when more than one LUKS device is involved (LP #2156681; the earlier assumption that #2143847 was this bug was wrong - that one is the software-db crash). Fixed in **3.3.14-0ubuntu25.26.04.1** (`resolute-updates`, verification-done); the package our image ships has not yet been re-checked against the fixed version, and a fix in the archive is not a VM result. HSCL1 refuses and explains rather than pretends; the fault-injection gate records the behaviour. Single-LUKS installs are not affected by that report. |
| Installer, unreachable apt source | upstream defect, mitigated by testing | Calamares can crash in the software-db step when a source is unreachable (LP #2143847, Fix Released in `calamares 3.3.14-0ubuntu21` + `calamares-settings-ubuntu 1:26.04.6`). The offline install is the primary tested path. |
| Virtual-machine screenshot share | unverified | The WSL2 host kernel has the 9p client (`/proc/filesystems` shows `nodev 9p`), but the virtio transport and the guest-side mount have not been proven yet; the visual-QA harness falls back to virtiofs or serial-console capture. |
| Neural Lab | PLANNED | No demo, Game Studio or workspace exists yet. Scope is deliberately small (neural cellular automaton, tiny-net trainer, toy frame predictor, grammar-validated game specs); nothing here is a neural game engine, and GameNGen/Genie 3 scale is out of reach on this hardware. |
| Release signing | not in place | Releases carry SHA256SUMS only; no signing key exists yet. |
| Network contacts inherited from the base | disclosed, not changed | With a network present, the installer contacts `networkcheck.kde.org` (connectivity check) and `geoip.ubuntu.com` (mirror choice); the installed system keeps the base defaults: time sync against `ntp.ubuntu.com` (chrony), package archives at `archive.ubuntu.com`, and the update-manager release check at `changelogs.ubuntu.com`. HSCL1 adds no telemetry of its own. Whether and how to replace these defaults is an open policy decision. |
| Live session names | VM test pending | The live session user and host name come from the first word of `/.disk/info` on the medium, which the image build sets to `HSCL1` (casper turns it into `hscl1`). Setting `FLAVOUR` in `/etc/casper.conf` instead broke the live boot (dev image r5) and is not used. Verified only after the VM test of the build that contains it. |
| HSCL1 keyboard shortcuts (AGENTS.md 4.5) | PLANNED | No HSCL1 shortcut binding exists in the repository (checked 2026-11-07: no tracked kglobalshortcutsrc/kwinrc/khotkeys file) and no user-facing doc or page publishes a shortcut table. Only the stock Kubuntu/KDE bindings of the base apply. Gate G11 therefore has nothing to audit yet; a table must not be published before the bindings and a test exist. |
| CQ-HECS in HSCL1 | partly integrated | The package `hscl-cqhecs` ships a launcher and a runtime pinned on demand. **The desktop entry only prints runtime status (`hscl-cqhecs doctor` in a terminal); it does not start the CQ-HECS Studio.** `hscl cqhecs status` (read-only) reports the package and runtime state by running the launcher's own `doctor --json`; `hscl mcp` has no CQ-HECS tool and the Control Center has no CQ-HECS card. The installed-system behaviour of `hscl-cqhecs run -- studio` has not been tested (checked 2026-11-08 in the package files). |
| CQ-HECS Studio local server (upstream, `timfromhcs/CQ-HECS` at `30c7f14`) | **security gap, not fixed** | The Studio's HTTP server (127.0.0.1, default port 8765) has no Host, Origin or token check and ignores the request `Content-Type`; its POST endpoints start solver jobs. Any web page open in the user's browser could trigger them while the Studio runs (resource use; code execution not shown). HSCL1 therefore does not start the Studio from the desktop entry. Read from source; no request was sent. Fix planned upstream (`docs/research/HCSPNP_DECISIONS.md` P2), pending owner approval for a CQ-HECS pull request. |
| CQ-HECS solver runtime in the OS | CPU engines only | The pinned OS runtime has no `python-sat`, so the CaDiCaL engine reports `unavailable`; only `watched`, `omniwave` and `scan` run. UNSAT from `watched` carries no certificate. `src/sat_solver.cpp` (native) is unaudited and not listed as a capability. |
| NP benchmark: DRAT proof checking | **RAT not implemented** | `tools/npbench/npbench/drat.py` reads the DRAT line format and checks every addition by RUP against the active clause database (deletions honoured). A step that is not RUP is reported `rat_unsupported` and the verdict stays `unknown`; the checker therefore accepts only RUP-only DRAT proofs, which is a strict subset of valid DRAT. No external solver was run through it, so "DRAT-checked" is not claimed for any third-party proof. |
| NP benchmark: scope | correctness, not competitiveness | The four families (SAT, graph, TSP, knapsack) use pure-Python solvers on small instances; the reports never compare them to CaDiCaL/Kissat or claim hardness results. No external instance set (TSPLIB, DIMACS, FHCP, MIPLIB) is downloaded or bundled - licence question open. |
| CQ-HECS DIMACS parser differential matrix (audit P1) | **recorded, partially measurable only** | `tests/unit/test_npbench_diff.py` pins our parser's behaviour for eleven input classes against the matrix in `docs/research/HCSPNP_BASELINE.md` (always runs). The second half executes the real `cqhecs.sat.parse_dimacs` and **skips with an explicit reason** when the local clone (`HSCL1_CQHECS_CLONE`) or an interpreter with qiskit (`HSCL1_CQHECS_PYTHON`) is absent - a CI runner has neither. The native C++ parser column of the audit table is **still read, never executed**: `cpp/` is not built in this workspace, so the native side of P1 is an audit finding, not a measurement. |
