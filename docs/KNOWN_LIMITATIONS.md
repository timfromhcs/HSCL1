# Known limitations (truthful list)

Status of this document: maintained with every phase. Last reconciliation: **2026-11-13** (queue and audit: [`AUTONOMOUS_QUEUE.md`](AUTONOMOUS_QUEUE.md), [`AUDIT_2026-11-10.md`](AUDIT_2026-11-10.md)). The published prerelease is `v0.1.8-alpha.0` (`def7f190…`, 5 027 201 024 B, built from `91c8acb`, xz, clean tree): UEFI boot at 4 GB, `qa_report.py` exit 0, every image gate green including `installer notes step stays disabled (Q-68)`, and **20 of 20 sequential installer starts survive with a core pattern set**. It is **not** a v1 release candidate: physical hardware, USB boot, TPM unlocking, a Tor-routed privacy session and release signing remain unverified. The installer crash that had been open since 0.1.4 (**Q-68**) is fixed: the `notesqml` step segfaulted in `prettyName()` while the progress tree painted it.

HSCL1 is **pre-alpha**. Nothing below has been tested on physical hardware. Rows are corrected whenever an earlier status turns out to
be stale - a limitation list that lags behind reality is a false claim in the other direction.

Image evidence is bound to its build. The published `v0.1.8-alpha.0` names source commit `91c8acb`; the newest local candidate, `HSCL1-rc12-amd64.iso`, is built from `e382047` and is **not** published. Neither proves the current `HEAD`: every VM result in this document is attached to the artifact named next to it. **Local evidence files:** `artifacts/` is git-ignored and was accidentally cleared on 2026-11-13 during a space cleanup ([BUILD_LOG](BUILD_LOG.md), "Incident"), so every `artifacts/...` path quoted here is historical and the measurements themselves are in that log. Secure Boot file signatures are not firmware acceptance. See [release readiness audit](research/2026-11-08-release-readiness-audit.md).

| Installer crashes intermittently at startup | **OPEN - the crash itself is unidentified; the SIGKILL that follows it is now explained**, mitigated by a bounded restart | The installer dies in about **one start in five** while it builds its first page: measured 2026-11-11 on rc4 with 10 starts in one boot, 4 up / 1 dead with the software-rendering wrapper and 4 up / 1 dead with `QT_QPA_PLATFORM=xcb`, so neither the GPU timing (software rendering is already forced) nor the platform plugin is the cause. The journal is always: `KCrash: appFilePath points to nullptr`, `KCrash: Application 'unknown' crashing`, drkonqi fails (`org.freedesktop.systemd1 exited with status 1`), then `Killed calamares -D8`, and the broken crash handler covers the screen. `/usr/bin/hscl-calamares` now dumps instead of spawning drkonqi (`KCRASH_DUMP_ONLY=1`) and restarts the installer if it dies within the first 60 s - a normal exit or a late crash is passed through, and three early deaths end the loop. Installs therefore succeed with a retry instead of failing outright. **The mechanism of the `Killed` line is established (2026-11-12):** an audit rule on `kill(2)` during 12 sequential starts recorded `sender drkonqi (pid 5919, ppid 5841) kill(pid=5841, SIGKILL) success=yes, victim pid 5841 comm=calamares` - drkonqi is forked by KCrash *from inside* the crashed Calamares, checks it with `kill(pid, 0)` and then SIGKILLs its own parent so it can gather a backtrace. That is why the exit status is 137 and why no core dump ever appeared: a SIGKILL never dumps. The wrapper's `KCRASH_DUMP_ONLY=1` was intended to suppress that drkonqi, but **it does not in this image** - six direct starts with the variable set still ended in 137 twice, like six without it, and `kernel.core_pattern=/tmp/cores/core.%e.%p` with `ulimit -c unlimited` produced zero cores in both series. What actually keeps an install possible is the restart loop, not that variable. The crash that starts the chain is still unidentified, but **its exact site is now known (2026-11-12, seventh probe):** with `chmod -x /usr/lib/x86_64-linux-gnu/libexec/drkonqi` KCrash re-raises the signal instead of starting its broken reporter, and the core dump gives a backtrace: `QListView::paintEvent` -> `QStyledItemDelegate::initStyleOption` -> `ViewManager::data` -> **`NotesQmlViewStep::prettyName()`** -> **`Calamares::Locale::TranslatedString::get(QLocale const&)`** -> SIGSEGV in `libcalamares.so.3.3`. So the crash is in the **`notesqml` step** - the notes page this image's hook inserts into the Calamares sequence - while the progress tree paints its name; 3 deaths in 12 starts that way, every one `rc=139`. Two earlier readings in this row were wrong and are corrected: **`crashRecursionCounter = 2` is the normal value for a first crash** (KCrash increments twice before printing), and **`KCrash: appFilePath points to nullptr!` comes from a second process** - the forked `drkonqi` with a different pid - which is the "Crash Handler has closed unexpectedly" dialog, not calamares. Naming the signal also required knowing that `KCRASH_DUMP_ONLY=1` and `KDE_DEBUG=1` cannot disable drkonqi here (Calamares enables it itself), which is why no core ever appeared. The rate is **environment-dependent by a factor of eight**: 1 death in 12 starts as shipped, 8 in 12 with `XDG_CURRENT_DESKTOP` set to empty, so the shipped environment is the good one and must not be "cleaned up"; the portal warning is not causal (survivors print it too). Queue row **Q-68** holds the detail, including the dead ends. |
