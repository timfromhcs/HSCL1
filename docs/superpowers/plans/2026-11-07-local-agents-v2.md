## Efficient CPU LoRA training through HCSUDA (owner 2026-11-07: "build hcsuda far enough that training is very efficient, then continue")
Scope decision: only the slice of HCSUDA that LoRA training on this machine needs; the rest of the unified masterplan (Vulkan, SAT, Studio) waits. Repository: local `C:\AI\work\hcsuda` (NVMe, new, not pushed, `timfromhcs/hcsuda` not created).
Facts from the QLoRA paper (read 2026-11-07) that shape the design: frozen 4-bit base weights are dequantized to the compute type on every use; LoRA on all linear layers; activations/input gradients, not adapters, dominate memory, so gradient checkpointing matters; per-block quantization metadata is a real cost (FP32 scale+offset per 64 weights = 1 extra bit per weight).
Hypotheses (estimates, NOT measured; each gets a measurement before it is believed):
1. Memory: Qwen3-4B bf16 base = about 8 GB; a 4-bit base with FP16 scale+offset per 128 = about 4.25 bits per weight = about 2.1-2.4 GB (the embedding/LM head may stay bf16). This is what lets training run next to nothing else on 20 GB.
2. Speed: forward+backward for a frozen base costs about 4 x params x tokens FLOPs (no weight gradients): 4 x 4e9 x 512 = 8e12 FLOP per 512-token step; at an assumed 150-300 GFLOP/s sustained fp32 AVX2 on 8 Zen3 cores that is 25-55 s per step. A fused int4-dequant GEMM can win only if the dequantization stays in registers; the baseline to beat is PEFT on the bf16 parent (measure it first: step time, RSS).
3. Gate for the HCSUDA kernel: bit-exact roundtrip against the Python reference (masterplan 3.1), matmul within a declared tolerance of the fp32 result, and a measured step-time win over the PEFT baseline; otherwise the slice is dropped and PEFT/bf16 stays.
Order: (a) baseline PEFT step time and RSS on the fp16 parent (needs the server stopped), (b) HCSUDA CPU core: QSTP Q4 offset codec (C++20, C ABI, ctypes), property tests, (c) AVX2 fused dequant-GEMM, (d) autograd glue (`torch.autograd.Function`, input gradient via the transposed product), (e) the same step benchmark, (f) only then train on real verified pairs (still gated: several hundred pairs, held-out set, 10-task bench not worse than 9/10 at <=10 s/task, rollback).
Toolchain facts: Windows has cmake, ninja, VS 2022 Community (vcvars64) and the Vulkan SDK; WSL has g++ 15.2, cmake, ninja (6 cores); the Python 3.14 install has CPU PyTorch 2.12.1, PEFT 0.19.1, Transformers 5.12.1, gguf 0.19.0, numpy. No `convert_lora_to_gguf.py` and no `llama-export-lora` exist locally (route to GGUF: fetch the converter script from the llama.cpp repo, MIT, or load the adapter via PEFT only).

### CPU training measured, and why the GPU stays idle (2026-11-07, evening)
- **Measured (`bench/train_step_bench.py` in the local hcsuda tree, Qwen3-4B-Instruct-2507, Q4 frozen base via HCSUDA, LoRA r=16 on all 7 linear layers, 33.0 M trainable parameters, gradient checkpointing, seq 512, CPU only):** median **57.6 s per step**, RSS 6.1 GB, one-time quantization of the bf16 parent 48 s. The earlier estimate of 25-55 s was at its optimistic edge; effective rate about 140 GFLOP/s against 260-360 GFLOP/s for an isolated dense matmul (attention, norms, the 151 936-token LM head and the decode passes cost the rest). 100 steps would take about 96 minutes: feasible, not "very efficient".
- **Why Task Manager's 3D graph does not move:** everything above runs on the CPU. The 680M is far faster for this kind of work: `llama-bench` prefill of the same model is 280 t/s, i.e. about 2.2 TFLOP/s effective, roughly 6x the CPU's dense rate. Leaving it idle is the main inefficiency. (Vulkan compute may also show under the "Compute" engine rather than "3D" in Task Manager; check both.)
- **GPU routes checked:** (a) official ROCm PyTorch wheels for Windows target Radeon 7000/9000 and a few Ryzen AI parts; the 680M (RDNA2) is not among them, no gfx1035 recipe found; (b) PyTorch has no Vulkan training backend; (c) **`tetherto/qvac-fabric-llm.cpp`** (MIT, pushed 2026-11-05, "QVAC Fabric": llama.cpp fork, additions under Apache 2.0 per the authors' blog) ships native **LoRA training on Vulkan** (`llama-finetune-lora`), verified for Qwen3 dense, quantized `OUT_PROD` and cross-entropy backward shaders, Q4/Q8/FP16/FP32 training paths, masked-loss SFT, checkpoints, `llama-export-lora` to merge, and AMD/Intel/NVIDIA/mobile GPUs; upstream llama.cpp only has the full-finetune `finetune` example with SGD on Vulkan. Its README documents `-ngl 999 -c 512 -fa off`, `--lora-rank`, `--lora-modules`. So **a GPU backend exists**; the work is to build it and measure the 680M, and to add what is missing around it (data pipeline from `rsi-capture`, benchmark gate, rollback).
- **Not done (blocked by the permission system, 2026-11-07 evening):** building the cloned fork (`C:\AI\work\qvac-fabric`, shallow clone of commit 2db8b046, build script `C:\AI\work\qvac-build.cmd`). Third-party code executes CMake/build scripts, so the owner has to approve that explicitly.
- **Host-device traffic on this APU (UMA):** heaps measured earlier: 9.1 GiB device-local, 4.55 GiB host-only, 256 MiB device-local + host-visible. VMA guidance: on unified memory prefer a host-visible + device-local type and skip staging; here only the 256 MiB heap has both flags, so weights (2.3 GB Q4) are uploaded once to the big heap and stay there; per-op activation traffic (512 x 2560 fp32 = 5 MB) can use the 256 MiB window as a ring. Lossless compression does not help: Q4 data is near-incompressible, bf16 exponent coding (DFloat11 about 30 % smaller, bit-identical) targets bf16 weights moved over PCIe, and there is no PCIe hop here. Measure the nibble entropy of the Q4 stream before any codec work.
- **Placement ("router") rule to implement and measure:** big-batch matmul/backward on the GPU with weights resident; decode and tiny ops on the CPU; the choice is a measured table per device (`hcsuda doctor`), not a guess.

### GPU training backend measured (QVAC Fabric, Vulkan on the 680M), 2026-11-07 evening
- **Built** `tetherto/qvac-fabric-llm.cpp` (commit 2db8b04, MSVC 19.44 + Vulkan SDK 1.4.357, owner-approved build): `llama-finetune-lora`, `llama-export-lora`, `llama-bench`. Startup line: `AMD Radeon(TM) Graphics (AMD proprietary driver) | uma: 1 | fp16: 1 | bf16: 0 | warp size: 32 | shared memory: 32768 | int dot: 1 | matrix cores: none` (no cooperative-matrix path in use on this driver).
- **Run** (Qwen3-4B-Instruct-2507 Q4_K_M, LoRA r=16 on all 7 linear modules, ctx/batch/ubatch 512, `-fa off`, 21 steps from 21 KB of text, process priority High, host hold set): after **4:17 min only 2 of 21 steps** (ETA 40:46, identical in two separate runs), i.e. about **2 minutes per step, roughly 2x slower than the CPU path (57.6 s)**.
- **Why Task Manager's 3D graph stayed flat (measured, not guessed):** Windows GPU-engine counters for the training process showed **no engine above 1 % utilisation**, while the process had accumulated 2057 s of CPU time in about 5 minutes, a 10.4 GB working set, **9.3 GB "shared" GPU memory and about 0 dedicated**, and the machine had only **1.8 GB free RAM**. So the training was CPU-bound with memory pressure; the GPU did not run the heavy ops. Dedicated memory on this APU is only the small BIOS carve-out; Vulkan allocates in shared system RAM, which is expected for `uma: 1` and is not something a flag changes by itself.
- **Not yet explained** (open, next experiments, one at a time): (1) which backward ops fall back to the CPU (`GGML_SCHED_DEBUG`, `GGML_VK_PERF_LOGGER` produced no usable output on a 1-step run); (2) whether `GGML_VK_PREFER_HOST_MEMORY=1` removes the duplicated host+device copy of the 2.3 GB weights (upstream llama.cpp b9668 changed the UMA default to host-visible buffers, PR 22930; whether the fork has that change is unchecked); (3) smaller `-c`/`-ub` to cut the compute buffers; (4) a 1-step run with `GGML_VK_PERF_LOGGER` to completion. A 2-datapoint run finished train+val in 2.6 s, so the full run's slowness is tied to size or memory pressure (hypothesis: paging; not verified).
- **Research results for "driver shortcuts, MTP, better compression, CPU+GPU together"** (web, 2026-11-07; none of this is a measured gain on this machine):
  - *Driver/memory:* no documented Windows AMD driver switch for iGPU compute was found; the levers are the ggml Vulkan environment variables (`GGML_VK_PREFER_HOST_MEMORY`, `GGML_VK_DISABLE_COOPMAT`-style switches), a warm shader cache, and the BIOS "UMA frame buffer size" (changes the dedicated carve-out; unverified benefit). Reports of Windows AMD UMA regressions after driver updates exist (Radeon 8060S), so the driver version stays pinned in every result.
  - *MTP:* multi-token prediction accelerates **inference** (FastMTP: 2.03x average with lossless output; a self-distilled 4-head MTP: +22.9 % speed; AdaMTP 2026) and can be trained with LoRA only (Apple gated LoRA, frozen decoder). It does **not** shorten a training step. Its use here is the RSI **data generation** speed (the 9B ternary server already used an MTP draft; the Qwen3-4B worker has no MTP head, training one would be a separate task).
  - *Compression:* LoftQ, ApiQ and LowRA improve the **quality** of 2-bit / sub-2-bit quantized LoRA bases and cut weight memory (a 2-bit 4B base is about 1.2 GB); they say nothing about a faster step, and training here is compute- and activation-bound, not weight-bandwidth-bound. Lossless codecs do not apply to Q4/UMA (see above).
  - *CPU+GPU together:* FusionML (Apple Silicon, arXiv 2607.22785, single-author preprint) measured a contention-aware row split of matmuls at 1.18x-1.38x for **prefill**, **no gain for decode** (shared bandwidth) and a **loss of 0.86x-0.97x for precision-matched training** (an earlier training "win" was retracted as a precision artefact). On a shared-RAM APU a combined CPU+GPU training step should therefore be expected to gain at most tens of percent, not "much better than either", until measured; a GPU-only step that really runs on the GPU is the first target (about 6x on the big matmuls by the `llama-bench` number).
- **Decision:** keep the CPU+Q4 HCSUDA path (57.6 s/step) as the working trainer; do not train on the QVAC GPU path until the CPU-fallback ops are identified and the step beats 57.6 s in a repeat run. Next measurements are listed above; each runs alone under `tools/hcs_hold.py`.
