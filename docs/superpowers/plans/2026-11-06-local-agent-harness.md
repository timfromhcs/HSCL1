## 1. What the sources say

### 1.1 The Mythos system card (PRIMARY, via extraction of the 245-page PDF)
Document: "Claude Mythos Preview System Card", https://www-cdn.anthropic.com/08ab9158070959f88f296514c21b7facce6f52bc.pdf (dated 2026-04-07 per search results; Anthropic states the model is not generally available).
- **Scaffold / harness.** The card only describes it in general terms: "agentic harnesses (software setups that provide them with extra tools to complete tasks)" (section 2.2.2); evaluations used search/research tools for red-teaming and knowledge tasks and "several domain-specific tools" for agentic tasks; five agentic runs tested whether "agentic scaffolding with expanded tool access" closes elicitation gaps (2.2.5.2); one research-task setup gave "a two-hour tool-call budget, access to a GPU, and a one-million-token allowance in a containerized environment with standard scientific Python libraries" (2.2.5.5); multi-turn evaluations used a **"think" tool** for interleaved thinking, with default sampling and no extended thinking (3.3). **No scaffold source code, prompt or full tool list appears in what we extracted.** A 1:1 rebuild is therefore impossible; only the *pattern* can be rebuilt.
- **Redactions.** The extraction found `[redacted]` markers inside an excerpt/observations table (section 2.3.5.1) and **no stated reason**. We do not know what was removed and must not guess it. (Search results also report a separate 59-page "Alignment Risk Update"; not read.)
- **RSI / automated AI R&D.** Defined through "Autonomy threat model 2": systems that "can fully automate, or otherwise dramatically accelerate, the work of large, top-tier teams of human researchers" in high-impact domains including AI itself; the card quotes RSP v3.1 operationalising this as (1) substituting for the entire set of research scientists/engineers at competitive cost or (2) dramatic acceleration (e.g. doubling) of the pace of AI progress through automation of AI R&D; the concern is a feedback loop where AI development accelerates AI development (2.3.2). Measured with a suite of automated research tasks (rule-out evaluations), internal surveys, a capability-trend slope-ratio measure (Anthropic ECI/AECI, item response theory) and external testing by METR and Epoch AI (2.3.3 to 2.3.7).

### 1.2 Later material seen only as search summaries (SECONDARY)
- A METR review of the automated-R&D section of Anthropic's August 2026 risk report (published 2026-11-05) says METR saw a private version, found the full-substitution argument broadly compelling, called the "below 2x acceleration" conclusion overstated, said it is plausible the threshold was crossed by 15 July, and that the public conclusion rests on judgment calls the public report does not make clear; it did not verify compliance with a specific policy threshold. https://metr.org/blog/2026-11-05-rd-section-anthropic-risk-report-august-2026-review/
- Coverage of an amended S-1 says internal estimates "may imminently meet" the RSP threshold while no current model has crossed it; policy version numbering differs between sources (v3.1 in the card, v3.4 in later coverage). **UNVERIFIED** beyond the snippets.
- Harness-design write-ups (first seen as SECONDARY summaries; **now read in the primary posts, see section 7, which supersedes this bullet**): an **initializer agent** prepares the environment and a **coding agent** makes incremental progress leaving artefacts (git commits, a progress file); a **feature list in JSON** is the external definition of "done" and the coding agent may only flip a pass/fail field; a later **planner / generator / evaluator** split with "sprint contracts" and rubric scoring targets "context anxiety" (finishing early as the context fills) and self-evaluation bias. Context compaction itself was not covered. https://www.creolestudios.com/anthropic-harness-design-for-reliable-ai-agents/ , https://www.mejba.me/blog/anthropic-long-running-agent-harness
- Anthropic's sandbox runtime uses bubblewrap on Linux plus a network-filtering proxy (SECONDARY, via the Sandlock paper https://arxiv.org/pdf/2605.26298); the same paper says bubblewrap/firejail have limited syscall control and weak filesystem semantics and pairs Landlock with seccomp-bpf. gVisor: user-space kernel, better isolation, compatibility and syscall cost for build tools; microVMs (Firecracker, Kata) recommended for arbitrary LLM-generated code with valuable assets in reach (blogs). **Nothing found on rootless Podman as an agent sandbox.**

### 1.3 Local-model reality (SECONDARY, mostly community reports)
- Scaffold-model fit matters: one report has the same 9B weights at 19.1 % in Aider versus 45.6 % with a scaffold adapted to small local models (anecdote); SmallCode claims 87 % single-file success with a 4B-active model through context budgeting, tool routing and tolerant parsing, capping tool output at 8000 characters by default (self-reported, https://pyshine.com/SmallCode-AI-Coding-Agent-Optimized-Small-LLMs/).
- Context pruning helps: Step 3.5 Flash keeps the problem statement and the last 50 % of history when over the limit; its ablation reports 48.03 % with a 16k cap plus pruning versus 45.22 % without and 50.98 % at the 64k baseline (https://arxiv.org/pdf/2602.10604).
- Open scaffolds: OpenHands (MIT, CodeAct in Docker, strongest open scaffold on SWE-bench Verified as of Dec 2025 per one paper), SWE-agent (MIT), Aider (Apache-2.0), Cline (Apache-2.0), OpenCode (many providers), mini-SWE-agent (about 100 lines, used for apples-to-apples model comparison). One source says quality floors at 32B-class local models; another reports a Qwen2.5-Coder-32B score on Aider's own benchmark; **no controlled comparison** found. SWE-Star (7B 36.4 %, 14B 52.8 %, 32B 57.1 %, scaffold forked from mini-swe-agent) shows trained small models can work but with a matching scaffold.
- **llama.cpp tool calling is fragile and moves fast:** fixes depend on the llama.cpp build, the GGUF's chat template and even the quant source (reports of tool-call failures fixed by rebuilding after a same-week patch, "think" tags leaking into context for Qwen 3.5, per-quant differences, vLLM reported more reliable for tool calls by one user). GLM, Vulkan iGPU and 24 GB RAM setups were **not** covered. Grammar-constrained decoding and a validate/retry layer are common mitigations; no comparison found.

## 2. What we can and cannot do (honest scope)
- **Cannot:** reproduce Mythos, its scaffold, its prompts, or its capability. No local model on this machine (24 GB RAM, Radeon 680M via Vulkan, no CUDA) approaches it; claiming parity would be false.
- **Can:** build a small, auditable **agent harness for local models** that applies the published *patterns*: tool-using loop, think tool, budgets, long-running initializer/worker/evaluator split, JSON feature list as definition of done, git-commit-per-step, progress file, sandboxed execution, context budgeting for small windows, tolerant tool-call parsing. Its purpose: help develop HSCL1 (tests, patches, docs) offline, on this machine.
- **Out of scope:** offensive-cyber automation. The Security Lab stays authorised-testing-only with the scope engine of the expansion plan (W18); the harness gets no network attack tools. Training or merging model weights stays out of this repository.
- **RSI in this repo means** a *bounded* loop that changes **our own tooling** under a guard (protected judge files, held-out checks, disposable sandbox, human approval to merge). It is not frontier AI R&D and makes no claim about it.

## 3. Design: `hcs-agent` (working name; extends the existing HCS Coder / OpenCode config)
1. **Decide build vs adopt (measure, do not assume).** Candidates: OpenCode (already in the owner's toolchain, MIT/Apache licence to check), mini-SWE-agent (tiny, auditable), Aider (diff-based editing, good with local models per sources), own minimal loop. Evaluate each on the **same in-repo task set** with the same local model; keep the one that wins on success per minute and per token, and stays auditable. Licence and pinned version recorded.
2. **Loop shape (from the patterns).** initializer (create `agent/features.json`, `agent/progress.md`, a git branch) -> worker (one feature per step, commit with message, update progress, may only set `passes` in the feature list) -> evaluator (separate prompt/model run, rubric + the real test command, cannot edit tests) -> stop on budget. JSON for the feature list (less likely to be casually corrupted than Markdown, a secondary-source claim we can test).
3. **Budgets (explicit, logged):** max tool calls, max wall time, max tokens per step and per run, max tool-output characters (start 8000, tune), history pruning rule (keep task statement + last 50 %, then measure).
4. **Think tool:** a no-op tool that records reasoning, enabled for models that benefit; measure with and without on the task set.
5. **Tool-call reliability layer:** pinned llama.cpp build + the GGUF's chat template recorded in the model profile; JSON-schema validation of every call; one repair retry with the validator's message; optional grammar-constrained decoding if the pinned build supports it; counters for malformed calls per 100 calls as a metric. Model/quant choices are decided by that metric, not by reputation.
6. **Sandbox (decide by measurement and threat model):** default = rootless Podman container with `--cap-drop=ALL`, `no-new-privileges`, read-only root, a single mounted workspace, **no network** (the Security Lab spec generator already builds this); alternative for lighter jobs = bubblewrap (+ Landlock/seccomp via a small wrapper) with a network-filter proxy. Anything that runs model-generated code that touches secrets or the network needs the stronger isolation (disposable VM). Not decided: whether bubblewrap is enough for our tasks; test escape attempts (write outside workspace, read `~/.ssh`, reach the network) as an automated suite.
7. **Memory/context:** progress file + feature list + git log are the long-term memory; compaction = rewrite of `progress.md` by the worker, reviewed by the evaluator; measure whether the local model keeps coherence over N steps.
8. **Interfaces:** CLI `hcs-agent run TASKFILE` (planned; listed in `--help` only when implemented), MCP server reuse with explicit annotations (master plan F9), results as JSON with hashes of the workspace before/after.

## 8. Guesses (explicitly hypotheses, each with the research found for or against it)
Nothing here is known about Mythos beyond section 1.1. These are my guesses about how such agentic work probably operates, written down so they can be tested on local models rather than believed.

|---|---|---|---|---|
| G1 | The scaffold is **thin**; capability comes from the model, not from clever orchestration | Anthropic's own SWE-bench scaffold is two tools and a plain prompt; "the model decides"; Anthropic advises direct API calls over frameworks | PRIMARY for the old setup, UNVERIFIED for Mythos | Start from a thin loop (bash + editor), add structure only where an experiment shows a gain |
| G1b | **But** small local models need *more* scaffold than a frontier model | Anecdote: same 9B weights 19.1 % vs 45.6 % with a small-model scaffold; SmallCode claims big gains from context budgeting and tolerant parsing; SWE-Star/DeepSWE trained *with* a matching scaffold | SECONDARY | Expect to add budgeting, validation, retries; measure each addition (A4-A8) |

## 9. Experiments added (A9-A12) and design deltas
- **A9 time horizon (own, small):** order the A1 tasks by our own estimate of human minutes, run each local model 3 times per task, fit success vs log-duration, report the 50 % task length with its spread. Needs at least 15 tasks spanning about 5 minutes to 2 hours of human time; otherwise report "not measurable".
- **A10 test-time scaling locally:** K = 1, 2, 4 independent rollouts with an execution-based selector (run the tests, prefer passing, break ties by smaller diff); report success per **wall-clock minute**, not per token, because that is our real budget.
- **A11 context hygiene:** tool-result clearing only, then + notes, then + compaction; measure success and tokens on a small window (8k, 16k, 32k).
- **A12 verification:** same task set with the evaluator's own test run vs the worker's claim; count false "done" claims; check that the worker cannot edit the feature list except `passes` and cannot touch tests (protected paths P17).
- **Design deltas to section 3:** (1) tools = `bash` + an editor with **absolute paths only**; (2) `agent/init.sh`, `agent/progress.md`, `agent/features.json` (`passes` is the only field the worker may change; checked by a script, not by trust); (3) session start routine = `pwd`, `git log`, read progress, read features, run the basic test, pick one feature; session end = commit + progress entry; (4) tool output cap starts at 8000 characters and is swept in A11; (5) budgets recorded in every run summary; (6) the think tool is off by default and enabled per model only if A5 shows a gain; (7) an optional LLM-judge call (single prompt, rubric, 0.0-1.0 + pass/fail) only for non-verifiable outputs such as docs; (8) subagents only when A3/A10 show a gain, and with an explicit cap on their number (the 50-subagent failure mode).
