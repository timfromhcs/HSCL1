### 1.2 Branch content versus `main`

The question that matters is not how many commits a branch has, but whether any
**file content** exists on a branch that is missing from `main`.

Method: for every branch, take the merge base with `main`, list the files the branch
touched, and compare the blob hashes of those files on the branch and on `main`.

```text
for each branch B:
  mb    = git merge-base main B
  files = git diff --name-only mb B
  drift = files where git rev-parse main:F != git rev-parse B:F
```

Result:

| Scope | Branches | Branches with content drift |
|---|---|---|
| Local branches (16) | all except `main` and `backup/pre-filter` | **0** |
| Remote branches `origin/codex/*` (23) | all | **0** |

Interpretation: the `origin/codex/*` branches still carry 1–2 unique commits each because
the PRs were **squash-merged**. Those commits are the pre-squash originals; their *content*
is already in `main`. No branch holds unmerged work.

`backup/pre-filter` is an old snapshot (490 commits behind `main`, 71 unique) and is
intentionally left untouched — it is a backup, not a work branch.

### 5.2 Lesson: measure the capture, do not trust the preview

While re-checking the Kate capture on 2026-11-11, the rendered preview of the PNG looked like a
white editor with black text, and that impression was written into the queue as "Q-53 reproduced".
The pixels said otherwise: the editor box (335,220)-(1010,600) has mean luma **43.1/255** and **0**
near-white pixels, the toolbar **50.4/255** — a dark Kate, exactly as the rc4 run claimed. The row
was corrected and the measurement is now quoted instead of the impression.

Rule for this repository: a colour claim ("dark", "washed out", "unreadable") must come from a
computed value over a named box, not from looking at the rendered image. Shape claims (a window is
missing, a label is slanted) are fine from the preview, because a preview cannot rotate glyphs.

## 6. Correction (2026-11-12): the installer logo is not stretched

§2.2 lists `docs/img/showcase/11_installer_welcome.png` as "The Calamares branding logo is **stretched
across the page**" and `PLAN_INDEX.md` repeated it as documentation debt. That is a **shape claim taken
from the preview**, and it is wrong. Measured on the capture itself:

| Quantity | Value |
|---|---|
| Source artwork `hscl1-lockup-light.png` (1024×211), visible-ink bbox | 976×183, ratio **5.333** |
| Rendered logo in `11_installer_welcome.png`, dark-ink bbox (382,422)-(1102,555) | 721×134, ratio **5.381** |
| Horizontal vs vertical scale | 721/976 = 0.739, 134/183 = 0.732 |
| Distortion | **+0.9 %**, i.e. within antialiasing and threshold noise |

The same numbers come out of `artifacts/q61-seq2/q61-seq2-log.png` (identical bbox), so this is the
page, not one capture. Calamares scales the welcome image with `PreserveAspectFit`, so it cannot
distort; `welcomeExpandingLogo: true` in `branding.desc` is exactly the switch that lets it fill the
page width, and that is what the "giant wordmark" is.

Verdict: **not a defect, no layout fix**. The page is a full-width hero logo above the language
selector, which is a deliberate composition, and `welcomeExpandingLogo` is set on purpose (its
neighbouring comment already documents the window-size decision made for the same page). Nothing was
changed in `branding.desc`. If the logo should be smaller, that is a design decision with a new
capture to judge it by - not a bug fix, and not "stretching".

Lesson, added to §5.2's rule: a **proportion** claim ("stretched", "squashed", "off-centre") is also a
measurement, not a preview judgement. A wide logo looks stretched to the eye precisely because it is
wide. Compare the rendered ink ratio against the artwork's ink ratio before writing the word.
